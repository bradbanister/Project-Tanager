Prompt:

I'm writing a C# application and I want to find out if there's a way to take JSON documents and serialize them into relational tables but do this without requiring code generation. The scenario is that these JSON documents have different shapes but I have metadata that explains what the document shape is and how that document should be translated for flattening into relational tables. I don't want to have to create a code generator to generate code for each document type, which is the standard way of both deserializing JSON and interacting with an object-relational mapper. I'd like it to be able to be runtime dynamic, where the application reads the metadata file and then from that is able to accept JSON documents of different types and can store them into the database. The same metadata will allow me to create the database schemas. Think deeply about this and suggest some ideas.

Response:

Of course. What you're describing is a **metadata-driven ETL (Extract, Transform, Load) engine**, and it's a powerful and flexible approach that avoids the rigidity of code generation. This is absolutely achievable in C\# without code generation by leveraging dynamic libraries for JSON parsing and database interaction.

The core idea is to treat the mapping logic as **data** (your metadata) rather than as **code**. Your application becomes an interpreter that reads this data to perform its work.

Here’s a breakdown of the concepts and the key components you'll need.

-----

## Core Concept: The Metadata-Driven Interpreter 🗺️

Think of your application as a generic engine. It doesn't know anything about "Customers" or "Orders" at compile time. Instead, it knows how to perform a few key tasks:

1.  **Read and understand a mapping document** (your metadata).
2.  **Parse any JSON document** into a generic, traversable structure.
3.  **Use the mapping rules** to pull values from the JSON structure.
4.  **Construct and execute SQL statements** (`CREATE TABLE`, `INSERT`) dynamically.

Your metadata file is the blueprint. The JSON document is the raw material. Your C\# application is the factory that uses the blueprint to process the raw material.

-----

## Key Components and Implementation Steps

You'll build this engine using a few key libraries and concepts.

### 1\. Define Your Metadata Schema

First, you need a consistent structure for your metadata files. JSON or XML are excellent choices for this. This metadata must describe the tables, columns, relationships, and the path to the data within the source JSON.

A good metadata structure would include:

  * **Entities:** An array of objects, where each object represents a database table.
  * **tableName:** The SQL table name (e.g., `dbo.Orders`).
  * **jsonPath:** The JSONPath expression to locate the object or array of objects in the source JSON (e.g., `$.orders`). If the path points to an array, the engine knows to create multiple rows.
  * **Properties:** An array of objects representing the columns in the table.
      * **columnName:** The SQL column name (e.g., `OrderId`).
      * **dataType:** The SQL data type (e.g., `INT`, `NVARCHAR(255)`, `DATETIME`).
      * **jsonPath:** The JSONPath relative to the parent object to find the value (e.g., `$.id`).
      * **isPrimaryKey:** A boolean to identify the primary key, useful for both schema creation and relating data.
  * **Relationships:** A way to define parent-child relationships, crucial for handling nested JSON. For example, linking `OrderItems` back to an `Orders` table.

#### **Example Metadata (`mapping.json`)**

Let's imagine you want to flatten this source JSON:

```json
{
  "purchase_event_id": "evt_123",
  "order": {
    "id": "ORD-500",
    "date": "2025-08-18T15:30:00Z",
    "customer_details": {
      "name": "Jane Doe",
      "email": "jane.doe@example.com"
    },
    "items": [
      { "sku": "A-001", "quantity": 2, "price": 25.50 },
      { "sku": "B-002", "quantity": 1, "price": 100.00 }
    ]
  }
}
```

Your metadata could look like this:

```json
{
  "entities": [
    {
      "tableName": "Orders",
      "jsonPath": "$.order",
      "properties": [
        { "columnName": "OrderId", "dataType": "NVARCHAR(50)", "jsonPath": "$.id", "isPrimaryKey": true },
        { "columnName": "OrderDate", "dataType": "DATETIME", "jsonPath": "$.date" },
        { "columnName": "CustomerName", "dataType": "NVARCHAR(255)", "jsonPath": "$.customer_details.name" },
        { "columnName": "EventId", "dataType": "NVARCHAR(50)", "jsonPath": "$.purchase_event_id", "isGlobal": true }
      ]
    },
    {
      "tableName": "OrderItems",
      "jsonPath": "$.order.items",
      "properties": [
        { "columnName": "OrderItemId", "dataType": "INT IDENTITY(1,1)", "isPrimaryKey": true },
        { "columnName": "ProductSKU", "dataType": "NVARCHAR(50)", "jsonPath": "$.sku" },
        { "columnName": "Quantity", "dataType": "INT", "jsonPath": "$.quantity" },
        { "columnName": "UnitPrice", "dataType": "DECIMAL(18, 2)", "jsonPath": "$.price" }
      ],
      "relationships": [
        {
          "parentTable": "Orders",
          "foreignKeyColumn": "OrderId",
          "parentPrimaryKey": "OrderId"
        }
      ]
    }
  ]
}
```

Notice the `isGlobal` flag—a custom addition to show how you can pull values from a higher level in the JSON tree.

### 2\. Dynamically Parse JSON

The standard `System.Text.Json` is good, but for this kind of dynamic traversal, **Newtonsoft.Json (Json.NET)** is often more powerful and flexible, especially its `JObject` and `JToken` API.

You'll parse the incoming JSON string into a `JObject`, which you can then query using the `jsonPath` from your metadata.

```csharp
using Newtonsoft.Json.Linq;

string jsonString = GetJsonDocument(); // Your source JSON
JObject root = JObject.Parse(jsonString);

// Using a path from metadata to get a value
string orderId = root.SelectToken("$.order.id")?.Value<string>();

// Using a path to get an array
JArray items = root.SelectToken("$.order.items") as JArray;
```

### 3\. Dynamically Interact with the Database

Since you don't have compile-time classes, you can't use standard Entity Framework Core `DbSet<T>` properties. Your best options are:

  * **Dapper:** A high-performance micro-ORM. It's perfect for this scenario because it excels at executing raw SQL queries and mapping results, but for `INSERT` statements, you can just use its `Execute` method with dynamic parameters. This is the **highly recommended** approach.
  * **Raw ADO.NET (`System.Data.SqlClient`)**: This is the foundational .NET library for database interaction. It's more verbose but gives you complete control to build `DbCommand` objects, add parameters, and execute them.

#### **The Processing Logic (The Engine)**

Your engine's workflow for inserting data would be:

1.  **Load Metadata:** Deserialize your `mapping.json` file into C\# objects.
2.  **Parse Source JSON:** Parse the incoming JSON document into a `JObject`.
3.  **Process Entities:** Loop through each `entity` defined in your metadata.
4.  **Get Parent PK:** First, process the parent table (`Orders`).
      * Find the JSON object using the entity's `jsonPath`.
      * Create a dictionary of parameters by looping through the entity's `properties`. For each property, use its `jsonPath` to extract the value from the JSON with `SelectToken`.
      * Build and execute a parameterized `INSERT` statement using Dapper or ADO.NET.
      * **Crucially**, retrieve the primary key of the newly inserted row (using `SCOPE_IDENTITY()` in SQL Server, for example).
5.  **Process Child Entities:** Now process the child table (`OrderItems`).
      * Find the JSON array using the entity's `jsonPath`.
      * Loop through each element in the array.
      * For each element, build the parameter dictionary just like before.
      * Add the **parent's primary key** (retrieved in the last step) to the parameters for the foreign key column.
      * Execute the `INSERT` statement for the child row.

### 4\. Schema Generation

The same metadata can be used to generate the `CREATE TABLE` statements. You'd write a separate utility function that:

1.  Loops through the `entities` in your metadata.
2.  Generates a `CREATE TABLE [tableName] (...)` script.
3.  Inside the parentheses, loops through the `properties` and appends `[columnName] [dataType]`.
4.  Adds `PRIMARY KEY` constraints based on the `isPrimaryKey` flag.
5.  After creating tables, loops through `relationships` to generate `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY` statements.

## Considerations and Trade-offs 💡

  * **Flexibility (Pro):** This is the biggest advantage. You can support new JSON formats and database schemas simply by creating a new metadata file. No code changes, no recompilation, no deployment.
  * **No Compile-Time Safety (Con):** You lose all static type checking. A typo in a `jsonPath` in your metadata will only be found at runtime, likely causing an exception. Rigorous testing is essential.
  * **Complexity:** The initial setup of the "interpreter" engine is more complex than a standard, statically-typed application. However, this one-time investment pays off if you deal with many different document types.
  * **Performance:** Dynamic parsing and reflection can be slightly slower than statically compiled code. However, for most business applications, the database interaction will be the bottleneck, not the JSON processing. Using Dapper will ensure the database part is extremely fast.
