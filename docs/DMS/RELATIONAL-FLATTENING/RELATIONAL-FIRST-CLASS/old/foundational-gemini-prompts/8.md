# Design Document: Relational Storage for Ed-Fi DMS API

This document proposes an alternative design for the Ed-Fi Data Management Service (DMS) storage layer. It replaces the current document-centric model with a dynamic, metadata-driven system that flattens API JSON documents into a normalized relational database.

-----

## 1\. Core Principles

This design is guided by the following principles:

  * **Metadata-Driven:** The entire system must be driven by the existing Ed-Fi DMS metadata that defines API endpoints and document shapes. **No code generation** for new endpoints should be required.
  * **Relational Integrity:** Data will be stored in a normalized relational schema with enforced foreign key constraints, ensuring data integrity and consistency.
  * **Dynamic & Extensible:** The system must automatically handle new or modified API resources by simply reading the updated metadata, without requiring application redeployment.
  * **High Performance:** The design must be optimized for both high-throughput writes (ingestion) and fast, structured reads (retrieval).

-----

## 2\. Schema Design Philosophy

The relational schema will be a direct, predictable reflection of the logical structure of the Ed-Fi JSON documents. A script can use the DMS metadata to generate this schema automatically.

### 2.1. Relational Structure 🔗

  * **JSON Root Object → Parent Table:** The top-level resource (e.g., `Student`) becomes the primary table (e.g., `dbo.Students`).
  * **JSON Nested Object → Flattened Columns:** A non-repeating nested object (e.g., `name`) is flattened into the parent table with a consistent prefix.
  * **JSON Array of Objects → Child Table:** An array (e.g., `studentSchoolAssociations`) becomes a child table (e.g., `dbo.StudentSchoolAssociations`) with a foreign key back to the parent.

### 2.2. Naming Conventions 🏷️

A strict naming convention is crucial for allowing the engine to infer relationships and mappings automatically.

  * **Tables:** PascalCase, pluralized (e.g., `Students`, `Schools`, `StudentSchoolAssociations`).
  * **Primary Keys (PK):** The pattern `[TableName]Id` (e.g., `StudentId`, `SchoolId`).
  * **Foreign Keys (FK):** The FK column in a child table will have the **exact same name** as the PK it references in the parent table (e.g., the `StudentSchoolAssociations` table will have a `StudentId` column).
  * **Flattened Columns:** The pattern `[Object]_[PropertyName]` for flattened nested objects (e.g., the `firstName` property in the `name` object becomes the column `Name_FirstName`).

-----

## 3\. Data Ingestion (JSON → Relational)

This section outlines two options for processing incoming `POST` and `PUT` requests.

### Option 1: Application-Side Flattening

In this model, the C\# application contains the logic to shred the JSON and insert it into the database.

#### **Workflow**

1.  The DMS API receives a JSON document for an endpoint (e.g., `/students`).
2.  The application loads the DMS metadata corresponding to the `Student` resource.
3.  The JSON is parsed into a dynamic `JObject` (using Newtonsoft.Json).
4.  The application logic iterates through the metadata:
    a. It uses JSONPath expressions from the metadata to extract values for the `Students` parent table.
    b. It generates and executes a parameterized `INSERT` statement for the `Students` table.
    c. It retrieves the newly created `StudentId`.
    d. It iterates through the `studentSchoolAssociations` array in the JSON. For each item, it generates and executes a parameterized `INSERT` into the `StudentSchoolAssociations` table, using the `StudentId` retrieved in the previous step.
5.  All database operations are wrapped in an explicit transaction (`TransactionScope`).

#### **Pros & Cons**

  * **Pro:** Business logic resides in the C\# application layer, making it easier to version control, unit test, and debug.
  * **Pro:** The solution remains database-agnostic (the same C\# code could target SQL Server or PostgreSQL).
  * **Con:** Less performant due to multiple database round-trips for a single JSON document.
  * **Con:** Higher risk of application failure leading to partial data writes if transaction management is not implemented perfectly.

### Option 2: Database-Side Flattening (Recommended)

This model moves the entire flattening and insertion process into a single stored procedure within the database, maximizing performance and atomicity.

#### **Workflow**

1.  The DMS API receives a JSON document.
2.  The application makes a **single call** to a stored procedure (e.g., `sp_InsertResourceFromJson`), passing the JSON payload as a single text parameter.
3.  The stored procedure uses native database JSON functions to shred the document:
      * **SQL Server:** `OPENJSON` with a `WITH` clause that defines the expected structure.
      * **PostgreSQL:** `jsonb_populate_recordset` and `jsonb_to_recordset`.
4.  The procedure inserts data into the parent and all child tables within a single, atomic transaction.

#### **Pros & Cons**

  * **Pro:** **Superior Performance.** Network latency is minimized to a single call. The database's native C++ code for JSON parsing is extremely fast.
  * **Pro:** **Guaranteed Atomicity.** The entire operation succeeds or fails as a single unit, eliminating the risk of partial data writes.
  * **Pro:** **Simplified Application Code.** The C\# application's role is reduced to routing, validation, and a single database call.
  * **Con:** Logic is encapsulated in database-specific T-SQL or PL/pgSQL, which can be harder to version control and test.
  * **Con:** Creates a tighter coupling between the application and the database vendor.

## 4\. Data Retrieval (Relational → JSON)

For `GET` requests, the design will use the database's native JSON generation capabilities to re-assemble the documents on the fly.

### Design: Database-Side JSON Generation

#### **Implementation**

1.  **JSON Views:** For each primary resource (e.g., `Students`), a database view (e.g., `vw_Students_JSON`) will be created.
2.  **Native JSON Functions:** This view will use the database's native functions to join the relational tables and construct the original nested JSON document.
      * **SQL Server:** The view will use `FOR JSON PATH` with specific column aliases (e.g., `s.Name_FirstName AS 'name.firstName'`) to rebuild the structure. The naming convention makes this aliasing predictable.
      * **PostgreSQL:** The view will use `json_build_object` and `json_agg` to assemble the nested objects and arrays.
3.  **API Interaction:** When the API receives a request like `GET /students/{id}`, the application executes a simple query:
    ```sql
    SELECT * FROM vw_Students_JSON WHERE StudentId = @id;
    ```
    The database returns a single column containing the complete JSON document as a string.

#### **Pros & Cons**

  * **Pro:** **Extremely Fast Reads.** This is the most performant way to serve the data, as all joins and aggregations happen within the database engine.
  * **Pro:** **Minimal Data Transfer.** Only the final JSON string is sent over the network.
  * **Pro:** **Consistent Output.** The shape of the JSON is defined and enforced by the view, guaranteeing consistency.
  * **Con:** The view definitions can become complex and are database-specific.

-----

## 5\. Recommendation

The recommended approach is to use the **database-side engine for both ingestion and retrieval**.

This design offers the best performance, highest data integrity through atomicity, and greatly simplifies the application-level code. While it introduces a tighter coupling to the database vendor, the benefits for a high-throughput, data-intensive service like the Ed-Fi DMS are significant. The systematic nature of the Ed-Fi data model and the proposed naming conventions will allow for the automated generation of the necessary stored procedures and views from the DMS metadata.
